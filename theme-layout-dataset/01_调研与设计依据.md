# 调研与设计依据

检索日期：2026-10-22。优先参考论文、作者项目页与官方仓库。下表的“原工作”是来源事实，“本项目采用”是针对主题布局的设计建议；不把建议写成原数据集的既有标准。

## 2. 对“全局元素太多”的具体判断

这个问题需要同时处理三件事，单纯减少框数不能保证模型学会布局：

1. **决策粒度**：模型究竟在移动一个时间组件，还是在猜每个数字、阴影、装饰的坐标？前者适合全局布局，后者大多属于组内渲染。
2. **监督内容**：标签是否表达了层级、关系、目标画布变化以及可执行的目标方案？仅有“时钟/天气”等类别只能教会识别，不能充分监督重排。
3. **数据变化与评价**：是否存在真正需要改变结构的目标、跨主题测试，以及与简单缩放/旧算法的对照？若只有同模板的颜色与时间变化，样本多也可能只学到模板。

据上述工作综合提出本项目方案：**自动提取事实 → 人工确认语义组件树 → 标关系与设计约束 → 人工确认目标重排 → 按任务导出**。这是一套待试标验证的项目规范，不是业界统一标准，也不承诺仅靠这种表示就能获得泛化能力。

## 3. 已有代码与本方案的差距

已检查 `src/multires_app/learning/`：

- `annotations.py`、`dataset.py` 可提供原始元素、组件推断与场景证据，推断角色仍需审核。
- `review.html` 可查看源元素/组框、编辑语义并调整既定目标根组；不能编辑完整组件树与关系图。
- `pairs.py` 可辅助原生双形态配对，但身份和状态对应仍需人工确认。
- `multires-layout/1` 只表达既定根组的目标 xywh，由求解器实现平移与统一缩放；不支持任意拆组、组内换序、新增/删除节点。
- 现有训练导出不能直接消费这里新增的完整结构/关系规范；不能把填写表单误称为已经训练接通。
- 当前真实弱候选构建会把算法目标组框放进 `inputLayout.groups`。如果把其自身答案用作生成任务监督，就会产生答案复制捷径。此问题已登记，尚未改动既有训练代码；正式接入前需采用第四份文档中的任务白名单导出方案。

因此，先用本规范完成少量人工试标并验证一致性，再决定扩展标注页和训练导出器；不应先大批量生成“已标注数据”。
