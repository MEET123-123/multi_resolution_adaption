短期落地：优先实现 Group Detector + 9 宫格 Anchor + Rigid/Row/Column/Overlay + 几何约束检查；复用现有 HTML 预览与 x/y/w/h 写回。

1. 项目背景、适用范围与验收边界
1.1 背景与现有痛点
传统几何缩放仅使用原始 x/y/w/h，缺少锚定关系、组件分组、视觉主次与容器排布信息。小幅尺寸变化下会产生间距漂移、公共组件不一致；长宽比变化显著时，还会破坏主体构图。主题并非普通 App 页面：文字常以图片资源形式出现，素材可叠加，部分元素是不可见交互热区，并且不同交互状态可能复用相同资产。

1.3 设计原则
“原来一致的继续一致，原来有意不同的保留差异”：跨场景继承只在确认同源、同设计意图时发生。
不把“同一水平线、同一高度”当作强制分组依据；它只能产生候选组。
布局 IR 与具体生成器解耦：规则、Kiwi、NCC、多模态都输出相同的最终坐标接口。
先判定结构可信度，再选择处理方法；低置信度时不强行锚点化。
只在被允许的 x/y/w/h 与系统参数范围内写回，资源 ID、触发器、脚本其他逻辑必须保持原样。

3.3 坐标系设计
统一外部输出为目标屏幕绝对像素坐标；组内部保留局部坐标，用变换将组内坐标转换成屏幕坐标。
为每个 bbox 标注 coordinate_space：source_screen、group_local 或 target_screen，防止多次缩放和坐标混用。
区分 script_bbox、render_bbox、visible_alpha_bbox：图片包含透明留白时，按 script_bbox 成组可能与人眼看到的对齐不一致。
每一条推断关系保留 provenance：手工、脚本语义、配对数据、几何规则或多模态建议。
4. 组件分组自动发现
图 2　从原始 bbox 到最终适配坐标的推断管线
4.1 前处理
1.  按场景状态过滤不可见元素；隐藏触发热区不参与视觉距离聚类，但与其所属内容保持绑定。
2.  获取 script bbox；若能从原始素材获得 alpha 轮廓，计算 visible bbox 作为第二证据。
3.  按 z_order / 渲染层分区，并标记占据整个屏幕的背景或大装饰，避免被纳入普通 Row。
4.  合并明显同源的过度切分素材候选组，但必须保留成员 ID 和原始相对变换。
4.2 Pairwise 关系特征
对空间相近的元素 A、B 计算：顶部/中心线/底部对齐偏差、尺寸比、水平或垂直间距、重叠占比、资源来源相关性、可见状态一致性、跨场景同步移动程度。公差建议按画布尺度和元素尺度自适应，不应使用固定的 5px 判定所有分辨率。
align_y(A,B) = min(|topA-topB|, |cyA-cyB|, |bottomA-bottomB|)
                 / max(1, median(heightA,heightB))
height_sim(A,B) = min(hA,hB) / max(hA,hB)
h_gap(A,B) = max(0, B.left - A.right)  # 已按 x 排序
overlap_ratio = intersection(A,B) / min(area(A),area(B))
 
score(A,B) = w1*alignment + w2*proximity + w3*size_sim
           + w4*semantic + w5*co_visibility + w6*paired_motion
# 各项归一化到 [0,1]，权重通过人工配对样本校准
4.3 组生成策略
推荐两阶段：先识别“局部高置信度配对”，再对群组执行结构验证；不要简单对关系图取全部连通分量，因为 A 贴近 B、B 贴近 C 不代表 A/B/C 全部应成组。
1.  用空间网格索引或 sweep-line 过滤候选边，避免数百元素执行昂贵的全量 O(n²) 关系判断。
2.  构建具有边类型的关系图（aligned / near / fixed_gap / same_asset_family / co_visible）。
3.  对每个候选集合尝试 Rigid、Horizontal、Vertical、Grid、Overlay 五种容器，计算排列误差与约束冲突。
4.  按 score、容器拟合误差、渲染层一致性输出候选组；允许嵌套组，例如时间图片子块 → 时间组 → 顶部信息组。
5.  置信度不足时保留自由元素，不强制归组；支持设计师在预览器中一键拆组/合组。

5. 锚点推断与坐标迁移
图 3　九宫格锚点与 Group 锚定示意
5.1 两级锚点
一级锚点：Group 相对于屏幕或父 Group；二级锚点：组内叶子元素相对于组容器或兄弟元素。Group 应同时指定 parent_point、self_point 和 offset，才能把“靠屏幕右上角”与“自身右上角贴靠屏幕右上”精确定义。
5.2 基本公式
Group.x = Parent.x + u * Parent.W - us * Group.W + dx
Group.y = Parent.y + v * Parent.H - vs * Group.H + dy
 
(u,v)  = parent anchor fraction, each in {0, 0.5, 1}
(us,vs)= self anchor fraction
(dx,dy)= signed offset defined in parent coordinate space
例：原屏幕 1080×2400，某 200px 宽的 Group 位于 x=800，距右侧 80px；目标屏幕 1260×2800，如果保持组宽且保持右侧 80px，则新 x=1260−200−80=980。与直接乘以 1260/1080 不同，该规则保持的是右边距。

5.4 锚点推断与“贴边或居中”判断
先计算组相对于屏幕四边与中心的归一化距离；构造 9 个候选锚点，再按“拟合源布局位置”和“人工目标布局迁移误差”共同排序。如果存在同一设计的人工多分辨率配对版本，应优先用配对数据学习锚点，而不是仅根据某一张图离哪个边最近来判断。
for group in scene.groups:
    candidates = 9_grid_anchors + percent_anchor_candidates
    for a in candidates:
        pred = transfer(group, a, source_size, target_size)
        err = normalized_bbox_error(pred, paired_designer_target)
        err += lambda_rel * internal_relation_deviation(pred)
        err += lambda_bound * boundary_penalty(pred)
    choose argmin(err) if margin(best, runner_up) > tau
    else mark anchor_confidence_low and route_to_solver_or_review
5.5 断点与多模式
不能只凭像素面积判断是否“尺寸变化不大”。建议使用宽高缩放率、长宽比变化、可用安全区域和 Layout Regularity Score 的联合判定。1080×2400 → 2560×1600 属于方向及长宽比剧烈变化，默认不进入只靠锚点迁移的通道。阈值初期可设为实验参数，通过已标注主题校准。

6.3 不要混淆几何包围盒与实际视觉尺寸
脚本 bbox 可能包含透明像素或嵌套可见层。若绘制尺寸能修改但素材不能裁剪，size_policy 必须根据资源的真实像素宽高、透明区和内容的重要性决定。对于时钟/天气图片资源，设置最小可视尺寸，避免目标屏幕缩小后不可读。
6.4 Figma/Responsive 思想的借鉴边界
Figma 的 Auto Layout 使用方向、gap、padding、固定/填充/包裹尺寸等机制，可借鉴为 Layout IR。对主题画面的艺术性构图不能“一律转 Flex”：大面积重叠和非规则留白需要 Rigid/Overlay/自由约束；可将 Figma 的自动建议布局思路用于候选组生成。
7. 约束求解与冲突恢复
7.1 约束级别
级别
示例
处理
Required / 必须
合法 bbox、非负宽高、公共组件锁定、不可改脚本字段

7.2 Kiwi 的使用范围
Kiwi 实现 Cassowary 线性约束求解，适合 x、y、w、h、对齐、边距、比例等线性/可线性化条件，以及不同优先级约束。[R3] 但“不允许两个矩形重叠”的方向选择属于析取/离散决策，不能无代价地用几条线性等式表示；不要将全部碰撞规避问题直接交给 Kiwi。
import kiwisolver as kiwi
 
x, w = kiwi.Variable('x'), kiwi.Variable('w')
canvas_width, margin = 1260.0, 80.0
s = kiwi.Solver()
s.addConstraint((w == 200.0) | kiwi.strength.strong)
s.addConstraint((x + w == canvas_width - margin) | kiwi.strength.strong)
s.addConstraint(x >= 0)
s.addConstraint(w >= 1)
s.addConstraint(x + w <= canvas_width)
s.updateVariables()
print(round(x.value()), round(w.value()))  # 980, 200
7.3 冲突解决流程
1.  预检测 required 约束和冻结的公共组件位置是否冲突；若冲突直接报告，不允许静默放松。
2.  先运行容器定位，再在组内计算并联立 Kiwi 线性约束。
3.  对存在非预期遮挡的元素对构造备选方向（A 左于 B 或 B 左于 A 等）；小范围枚举方向后由 Kiwi 解，复杂时考虑 OR-Tools CP-SAT。
4.  若失败，按 weak → medium → strong 顺序减少软约束并记录冲突来源；required 永远不能自动降级。
5.  通过硬约束、渲染评测且优于上轮得分后才接受方案；否则回滚到最佳历史布局。
7.4 哪些重叠不能禁止
主题经常设计为人物遮住背景、装饰部分覆盖主体、粒子覆盖文字边缘。仅在业务定义“不可遮挡”的元素对上检查相交。保留原 z_order 与合成规则，不能再用“元素像素越小越置顶”替代真实渲染语义；若当前渲染器顺序规则尚未核实，应把层级准确性列为独立阻断项。
8. 跨场景一致性、交互与渲染顺序
8.1 共用组件的全局绑定
同一主题中公共组件可在多个可达状态中复用。先从 Skill C 场景聚类中生成 canonical_group_id，再对同一组创建“共享的 Group Anchor + Size Policy”；各场景继承位置，不允许重复由模型独立生成。但在原设计本就有意变化的状态，须记录 override_reason。
global_group: public_time_top
  base_constraints: anchor=top_center, scale=uniform
  inherited_by: [scene_01, scene_02, scene_05]
  overrides:
    scene_07: {reason: 'designer_intent_variant', anchor: bottom_center}
8.2 分组时纳入可达状态
单张截图只能观察当前可见资源。互斥资源与绑定热区可能无法同时出现，需从脚本状态机获得变体对应关系；遵循已确定的 P0 基准帧、P1 互斥覆盖、P2 高风险组合、P3 固定时间/日期/电量、P4 动画按需补帧。动态资源的时序验证仍不属于静态 Anchor V1 的已验证能力。
8.3 视频和序列帧的预留接口
元素模型中保留 asset_type、frame_count、fit_mode、timeline_ref、reference_frame、content_rect 等字段，但短期仅在参考稳定帧上检查几何结果。后续必须评测裁剪轨迹是否连续、跨帧主体是否漂移、序列帧组的整体统一变换、编码分辨率与显存/存储开销；不可按静态单帧通过率宣称动态适配可用。
9. 多模态重排与截图反馈闭环
9.1 将 MLLM 定位为低置信度兜底
对长宽比剧变、组结构复杂、锚点不确定的场景，由多模态模型提出初始 bbox 或局部修正建议，然后统一通过同一 Layout IR、硬约束与写回校验。纯多模态模型不能替代脚本状态推导、必需约束和确定性场景复用。

9.3 迭代安全控制
模型只返回 element_id / group_id 对应的 delta(x,y,w,h)，默认不允许改变资源引用、z_order、交互 ID。
每轮对修改幅度施加信任域约束（例如不超过可用宽高的特定比例，阈值需实验确定）；锁定公共组件不能改。
保留 best-so-far，不以最后一轮自动覆盖最好一轮；迭代次数与推理预算有上限。
视觉 critic 检测构图偏移，程序检测越界、合法性、关系及组件一致性；设计意图冲突需要设计师复核。
全图检查后对高风险局部区域裁剪截图，再反馈给模型，减少不必要的全图视觉推理开销。
9.4 与 NCC 模板匹配的结合
当前已有 NCC 模板匹配路径，可将“预期渲染图 vs 当前渲染图”的候选位移用于定位误差较大的子元素，作为 Kiwi/MLLM 修正建议之一。需要处理尺度变化、遮挡、重复纹理、透明像素带来的匹配误差；对低置信度匹配不自动写回。[R7]

11.5 MVP 门槛（需评审确认）
功能正确性门槛：只修改白名单字段；无非法 bbox；场景结构及脚本逻辑不变；失败自动回滚。

12.1 优先研究的源代码和接口
ConstraintLayout：重点阅读核心 widget/ConstraintAnchor、Chain/Guideline/Barrier/Flow 的约束表达；抽取概念与测试用例，而不是复制 Android UI XML。[R1]
Kiwi：先直接安装 kiwisolver，在 Python 中原型化组锚点、组内对齐和 required/strong/weak 优先级，并用单元测试验证约束冲突与解除策略。[R3]
Yoga/Taffy：编写相同的“3 个图标 Row、带变宽标题 Column、2×3 Grid”输入样例，比较与自研容器坐标的差异。对 Rigid/Overlay 继续使用自研逻辑。[R2][R4]
UIED + OpenCV：截图分割和 NCC 仅作为辅助证据；主数据仍应以内部解析脚本 bbox、资源与交互元数据为准，降低数据丢失风险。[R6][R7]
12.2 直接接入的建议顺序
1.  第 1 优先：自研 Group/Anchor + 轻量 Python 容器布局；避免过早引入复杂依赖。
2.  第 2 优先：kiwisolver，优化软硬约束并输出可解释失败报告。
3.  第 3 优先：OpenCV/NCC 位移建议接入同一修改接口。
4.  第 4 优先：当出现高频 Grid/Flex 复杂容器，再单独评估 Taffy 或 Yoga；不要同时嵌入两个引擎。
5.  第 5 优先：针对必须做离散方向选择的场景局部启用 OR-Tools CP-SAT。

13.4 关键设计决策建议
建议立项 AnchorLayout V1，而非一次性做“所有主题自动响应式”。先测量 Group 识别准确性、锚点迁移效果和人工修正成本；只有 A/B 数据显著支持时，才扩大算法覆盖范围。
附录 A：核心算法伪代码
def adapt(scene_ir, target_viewport, model=None):
    normalized = normalize_source(scene_ir)
    graph = build_sparse_relation_graph(normalized.elements)
    groups = infer_groups(graph, script_semantics=normalized.metadata)
    groups = validate_hierarchy(groups, forbid_cycles=True)
    anchor_candidates = infer_anchors(groups, normalized.viewport)
    strategy = route_layout(groups, anchor_candidates, target_viewport)
 
    if strategy == 'ANCHOR':
        proposed = layout_anchor_containers(groups, target_viewport)
    elif strategy == 'SOLVER':
        proposed = solve_with_kiwi(groups, target_viewport)
    else:
        proposed = model.propose_layout(normalized, target_viewport)
        proposed = enforce_constraints(proposed, groups, target_viewport)
 
    validation = validate_bbox_constraints(proposed, normalized)
    render = render_preview(proposed)
    metrics = evaluate(render, normalized, validation)
    if not validation.required_ok:
        return FAILURE_WITH_REPORT
    return AdaptationResult(proposed, metrics, validation)
附录 B：单元测试与回归清单
1.  Group：三张水平图标可正确归为 Row；同高度但空间远离的两个主体不误归组；背景不与内容 Row 混合。
2.  Anchor：右上角组在目标画布扩大时保持右边距；中心组保持中心；归一化位移单位正确。
3.  Container：Row 保序、Column 保序、Rigid 相对位置保持、Overlay 保留 z_order 与允许重叠。
4.  Solver：强约束不能自动降级，软约束冲突返回解释；不允许的碰撞组合不通过。
5.  Scene：同组公共组件跨场景继承；设计差异 override 保留；可达状态签名可复现。
6.  Writeback：脚本仅 x/y/w/h 和批准系统变量发生变化；任何资源引用、层级或触发器差异拒绝写回。
7.  Visual：多个目标分辨率回归；HTML 预览和真实主题渲染对齐的差异单独检查。
8.  Dynamic：视频和序列帧明确标为尚未通过，不借静态结果覆盖验收。
