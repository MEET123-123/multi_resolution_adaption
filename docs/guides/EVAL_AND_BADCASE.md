# 批量评测、badcase 归因与反向优化

> 本文保留早期汇总分析。下面的 candidate 回归数和告警数不能直接等同于最终产物的确认缺陷。逐场景判定、可复现证据、人工反馈、候选接受和固定回归请使用 [可插拔反馈闭环](FEEDBACK_LOOP.md)；历史报告未绑定当前候选时不会被该闭环当作通过。

面向"主题量上来以后怎么知道哪里变差了、为什么变差、改哪一层"的工程方案。当前仓库已有 24 个真实主题、25 个项目、550 个项目×设备、1670 个采样状态的产物，可以直接当作第一版评测集，不需要等新数据。

## 一、先看清现状：三层资产，一个缺口

| 已有资产 | 位置 | 覆盖 |
| --- | --- | --- |
| 结构校验 | `scenes/validation.json`、`live-validation.json` | XML 解析、ZIP 条目与哈希、采样几何、冻结组件、单次完整手势 |
| 几何质量门 | `scenes/anchor-layout.json` 的 `devices.*.quality` | 裁切、重叠、屏幕关系、资源缩放、冻结漂移，含候选与基线对比 |
| 美学代理 | `project.json` 的 `aestheticEvaluation` | 十维损失、优化前后分数、候选接受/拒绝原因 |
| 归因原料 | `layouts[].adaptationReview`、`graph.coverage`、`diagnostics` | 97,279 条审查记录、覆盖度、解释器告警 |

**缺口不是"没有指标"，而是指标没有被汇总、切片和归因。** 现有结论是"6,672 个采样快照、0 失败"，同时并存 97,279 条 `adaptationReview` 告警和 71.6% 的设备美学分未提升。聚合口径把真实分布掩盖了。

`multires.py tools eval-batch` 补的就是这一层：只读扫描，不改动任何产物，把四类原料压成一条 `项目×设备` 记录，再按固定编码归因。

## 二、指标体系：五层，从"对不对"到"好不好"

| 层 | 回答的问题 | 指标 | 判据 |
| --- | --- | --- | --- |
| L0 结构 | 产物是否可交付 | validation failures、live failures、ZIP 哈希、冻结漂移 | 必须为 0，硬门禁 |
| L1 几何 | 是否比基线更差 | 重叠率、裁切率、屏幕关系违规率、资源缩放误差/快照 | 相对基线，禁止局部退化 |
| L2 美学 | 好不好看（代理） | 十维加权分、主导损失维度、接受步数 | 分位数 + 切片对比 |
| L3 覆盖 | 结论可不可信 | 状态数、触发器采样率、手势预算、低样本标记 | 低覆盖不进 P0 |
| L4 交互 | 操作是否成立 | 手势成功、返回恢复、命中区遮挡 | 必须为 0，硬门禁 |

**关键约定**：L0/L4 是门禁，L1/L2 是趋势，L3 决定这条记录能不能参与排名。低样本设备（快照 < 50 或状态 < 5）一律降级为 P1，避免 8 个快照里 2 个重叠就算 P0 的假精度。

## 三、第一版评测集的真实结论

跑完 25 个项目、550 个项目×设备后的结果：

| 切片 | 设备 | 均分 | 最低分 | 重叠率 | 裁切率 | 审查/布局 | 重叠回归 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| portrait | 250 | 92.69 | 72.19 | 1.93% | 0.40% | 1.57 | 41 |
| landscape | 250 | 80.59 | 46.67 | 6.10% | 1.22% | 3.43 | 114 |
| square | 50 | 82.65 | 68.40 | 5.08% | 1.22% | 2.40 | 18 |

三个可以直接立项的问题：

1. **横屏是系统性短板**。均分低 12.1 分，重叠率高 3.2 倍，审查密度高 2.2 倍，重叠回归占全部回归的 63%。这不是个别主题的问题，是宽画布下的缩放与锚点策略问题。
2. **质量门的回滚条件是"全指标占优"**。`layout_quality.py` 里 `worse and all(previous<=candidate)` 要求基线在**每个**指标上都不差于候选才回滚；只要屏幕关系误差改善（基线 4100 万 px vs 候选 62 万 px），重叠和裁切退化就永远进不了回滚。结果 550 台设备 100% 选中 anchor，其中 173 台重叠数高于基线、54 台裁切数高于基线。
3. **优化器 71.6% 的调用是空转**。550 台里 394 台 `no admissible improvement found within budget`，拒绝原因集中在 `source-axis-gap`（484）和 `state-score-floor`（320）。约束把可行域压得只剩原点附近，48 个候选全部被拒。

## 四、归因方法：编码 → 证据 → 阶段 → 热点

每条 badcase 固定四段，避免"看起来像布局问题"的口头归因：

```text
code（稳定编码） → evidence（可复算的数字） → stage（管线阶段） → hint（具体模块）
```

| 编码 | 问题 | 阶段 | 触发证据 |
| --- | --- | --- | --- |
| GEO-01 | 新增非预期重叠回归 | layout | 候选重叠数 > 基线 |
| GEO-02 | 新增裁切回归 | layout | 候选裁切数 > 基线 |
| GEO-03 | 组件超出安全区 | layout | `adaptationReview` 计数/布局 |
| GEO-04 | 组件低于最小缩放 | layout | 同上 |
| GEO-05 | 同场景新增重叠 | layout | 同上 |
| GEO-06 | 屏幕关系误差偏高 | layout | 违规数/快照 |
| GEO-07 | 资源缩放偏差偏高 | media | 误差 px/快照 |
| GEO-08 | 冻结组件漂移 | layout | `fixedTransformDrift > 0` |
| AES-01 | 低分且无可行改进 | aesthetic | score < 80 且 acceptedSteps = 0 |
| AES-02 | 美学维度瓶颈 | aesthetic | 最大加权损失占比 > 0.45 |
| COV-01/02/03 | 探索截断 / 触发器不足 / 手势预算耗尽 | interaction | coverage 字段 |
| AST-01/02 | 素材未解析 / 表达式未解释 | engine | diagnostics |
| EXP-01 / INT-01 | 反写失败 / 交互验证失败 | export | validation / live |

本轮 1,743 条 badcase 的分布：layout 1,193（68%）、aesthetic 325、media 142、interaction 42、engine 41。**归因把 68% 的问题钉在布局层，而不是笼统的"适配效果不好"。**

组件热点（跨主题高频）：`Video[1]` 7,506、`Group[1]` 7,428、`Group[6]` 5,842、`Image[5]` 4,787。视频类组件反复触发"超出安全区"，说明不可等比缩放的媒体需要独立的缩放族策略，而不是逐组件调参。

## 五、反向优化：让评测驱动改动

### 1. 三层数据集，不要一个大集合

| 集合 | 来源 | 用途 | 规模建议 |
| --- | --- | --- | --- |
| 回归集 | 当前 25 个项目全量快照的指纹 | 每次改动跑，任何指标回退即失败 | 550 设备 / 1,670 状态 |
| 困难集 | P0/P1 badcase 固定样本 | 修一个验一个，防复发 | 100–200 条，版本化 |
| 校准集 | 人工标注的成对偏好 | 校准代理分与真人判断的一致性 | 每切片 30–50 对 |

困难集要**冻结**：`eval/badcases.jsonl` 里挑出来的条目复制到 `eval/hard-set/`，附带期望结论（应通过/应被标记）。否则修完就忘，下轮又退化。

### 2. 改动门禁：从"总均分"改成"逐指标预算"

```text
允许：某指标改善，其他指标不动
禁止：任何指标恶化超过预算（重叠 +0.5%、裁切 +0.2%、均分 -0.3）
必须：P0 数量不增加
```

`--compare` 已实现逐设备 diff，输出 `eval/regression.json`。把它接进 CI，作为 `release-readiness` 的前置条件。这一步直接修掉第二节第 2 条的设计缺陷：把"全指标占优才回滚"换成"任一指标超预算就回滚或人工复核"。

### 3. 反事实对比，产出算法选择器

现有 `anchor-layout.json` 同时保存了 `candidate` 与 `baseline` 两套指标，这本身就是一份**免费的 A/B 数据**。按切片统计谁赢：

- 横屏、宽高比 ≥ 1.9 时 anchor 的重叠更差 → 该切片优先走 baseline 或调缩放族
- 竖屏时 anchor 全面占优 → 保持默认

累计到几百条后，可以训练一个轻量选择器（特征：宽高比、组件角色分布、媒体占比、状态数），在 `finalize_anchor_device` 里按预测结果选算法，而不是全局默认 anchor。

### 4. 人评校准，别让代理分自说自话

当前 `humanCalibrated: false`、`designerGoldLabelsAvailable: false`，十维权重是拍的。校准流程：

1. 每切片抽 30–50 对（原图 vs 适配图），设计师只做**二选一**，不做打分
2. 计算代理分差与人工偏好的 Spearman 相关
3. 相关性 < 0.5 的维度降权或重写；> 0.7 的维度固化
4. 校准结果写回 `layout_aesthetics.DEFAULT_WEIGHTS`，并在报告里标注校准版本

没有这一步，所有"均分 86.28"都只是内部自洽。

## 六、落地路线

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| 第 1 周 | 跑通 `eval-batch`，冻结回归集与困难集，把 `--compare` 接进 CI | `eval/` 四个文件 + CI 门禁 |
| 第 2 周 | 修质量门（逐指标预算替代全指标占优），重跑全量 | 重叠回归 173 → 目标 < 30 |
| 第 3 周 | 攻横屏切片：缩放族、锚点、不可缩放媒体（Video） | landscape 均分 80.6 → 85+ |
| 第 4 周 | 放宽优化器可行域，降低 `source-axis-gap` 拒绝率 | 空转率 71.6% → 50% 以下 |
| 第 5 周起 | 人评校准 + 算法选择器 | 校准报告 + 选择器 |

## 七、命令

```powershell
# 全量评测与归因（只读，写出 eval/）
.\.venv\Scripts\python.exe .\multires.py tools eval-batch

# 只跑指定项目
.\.venv\Scripts\python.exe .\multires.py tools eval-batch --only wufu beihai

# 与上一次基线比较，输出回归项
.\.venv\Scripts\python.exe .\multires.py tools eval-batch --compare eval/baseline-scorecard.json
```

产物：

| 文件 | 内容 |
| --- | --- |
| `eval/scorecard.json` | 550 条项目×设备记录 + 全部分组聚合 |
| `eval/badcases.jsonl` | 逐条 badcase，含编码、证据、阶段、定位建议 |
| `eval/attribution.json` | 按编码/阶段/切片/主题的分布 |
| `eval/regression.json` | `--compare` 时的逐设备回归项 |
| `eval/report.html` | 可直接查看的看板 |

## 八、边界

- 评测读的是产物，不重新布局；布局代码改动后必须先重跑 `batch-convert` 或 `iterate-*`，否则评的是旧结果。
- 所有指标都是几何与统计代理，不含真人审美判断；`report.html` 里的风险指数只用于排序，不作为验收结论。
- 低样本设备（状态 < 5 或快照 < 50）标记 `lowConfidence`，不参与 P0 判定。
- 覆盖度不足的主题（18/24 触顶截断、5 个主题仅 2 个状态）会系统性低估问题，扩状态预算前不要用它们的均分做跨主题比较。
